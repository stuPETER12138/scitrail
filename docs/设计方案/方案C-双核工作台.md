# 方案 C · 页面+表格双核工作台（Notion 式）

| 一句话定位 | 一切皆页面，页面里可内嵌"数据库"并切换表格/看板/日历视图——把 Notion 的表达力搬回本地 |
|---|---|
| 交互重心 | 页面树 + 内嵌数据库视图 |
| 数据范式 | 文档表 + JSON 记录表（文档驱动） |
| MVP 工作量 | 约 15~25 个集中开发日 |
| 成长路径 | ★★ 自成一派，表达力天花板高但工程量最大 |

---

## 1. 核心理念

- 系统的骨架是**一棵页面树**：仪表盘、每个课题、每篇论文、每次组会都是树上的一页；
- 页面正文是富文本/Markdown，可以**内嵌"数据库块"**：一块数据库 = 一组结构化记录（如"10月任务"），同一块数据可切换表格/看板/日历/看板视图；
- 不预定义"课题页该长什么样"——用**页面模板**解决：建"课题页模板"自带任务数据库块 + 实验数据库块 + 资料块，新建课题时一键套用；
- 这是五个方案中唯一把"知识笔记"和"事务管理"装进同一个模型的选择。

## 2. 借鉴的开源项目

| 项目 | 借鉴点 |
|---|---|
| [思源笔记 SiYuan](https://github.com/siyuan-note/siyuan) | 本地优先 + 块级 SQLite 索引：内容存文档、索引存数据库，两全；块引用/反链实现 |

| [Baserow](https://github.com/baserow/baserow) | 字段类型体系（文本/单选/日期/关联/ Lookup），内嵌数据库的字段设计参考 |

### 3.2 页面清单（8 类）

页面树 / 页面编辑器（富文本+数据库块）/ 数据库视图（表格/看板/日历）/ 页面模板管理 / 仪表盘（聚合页）/ DDL 库（全局数据库块+倒计时组件）/ 全局搜索 / 设置

### 3.3 关键交互

- **模板建课题**：新建课题 → 选"课题模板" → 自动生成带 4 个数据库块的课题页；
- **跨页引用**：仪表盘插入"引用视图"——显示各课题页里的任务数据库的汇总（Notion linked database 思路）；
- **块引用/反链**：周报里 `@引用` 某条实验记录，自动生成反向链接；
- 同一份数据库记录在表格/看板/日历间切换（AppFlowy 模式）。

### 3.4 视觉风格

Notion 风：无侧边栏分割线的页面树、图标+封面、内容区宽松排版；数据库块带工具栏。

## 4. 数据库设计

### 4.1 表清单（7 张）

| 表 | 职责 |
|---|---|
| document | 页面树（标题+正文） |
| db_def | 数据库定义（字段 schema JSON） |
| record | 数据库记录（fields JSON） |
| view | 数据库视图配置 |
| backlink | 块/页面引用关系 |
| ddl | 独立 DDL（倒计时组件直接读） |
| setting + template | 配置与页面模板 |

### 4.2 核心表 DDL（SQLite）

```sql
CREATE TABLE document (
  id         INTEGER PRIMARY KEY,
  parent_id  INTEGER REFERENCES document(id) ON DELETE CASCADE,
  title      TEXT NOT NULL,
  body       TEXT DEFAULT '',      -- Markdown 或块 JSON（二选一，MVP 用 MD）
  icon       TEXT, sort REAL,
  created_at TEXT DEFAULT (datetime('now')),
  updated_at TEXT
);

CREATE TABLE db_def (
  id     INTEGER PRIMARY KEY,
  name   TEXT NOT NULL,
  fields TEXT NOT NULL   -- JSON schema:
                         -- [{"name":"状态","type":"select","options":["待办","进行中","完成"]},
                         --  {"name":"截止","type":"date"},{"name":"参数","type":"text"}]
);

CREATE TABLE record (
  id         INTEGER PRIMARY KEY,
  db_id      INTEGER REFERENCES db_def(id) ON DELETE CASCADE,
  fields     TEXT NOT NULL DEFAULT '{}',
  created_at TEXT DEFAULT (datetime('now')),
  updated_at TEXT
);
CREATE INDEX idx_record_db ON record(db_id);

-- JSON 查询示例：某库中"截止在7天内且状态≠完成"
-- SELECT * FROM record WHERE db_id=3
--   AND json_extract(fields,'$.截止') <= date('now','+7 day')
--   AND json_extract(fields,'$.状态') != '完成';
```

### 4.3 设计取舍

- **字段中文化存在 JSON 里**：界面即 schema，加字段零迁移——但统计查询全部走 `json_extract`，毕业对照这类聚合是硬伤；
- **正文选 Markdown 而非块 JSON**：块编辑器（可拖拽的 block 富文本）本身是 2~4 周的工程，MVP 用 Markdown + 少量内嵌块语法；
- **反链表显式建**：引用关系落库，周报引用实验记录可双向跳转。

## 5. 对需求报告的覆盖度

| 需求模块 | 覆盖情况 |
|---|---|
| 课题 / 任务 / 文献 / 资料索引 / 周报 | ✅ 全部能装（页面+数据库块） |
| 实验记录 | ✅ 完整（=实验数据库块） |
| DDL / 里程碑 | ✅ 完整（全局 DDL 库+页面内倒计时组件） |
| 论文流水线 | ✅（看板视图） |
| 成果对照 / 统计 | ⚠️ 聚合统计弱（JSON 扫描），图表需另做 |
| 仪表盘 | ⚠️ 是"聚合页"而非真仪表盘，实时性一般 |

## 6. 优缺点与风险

**优点**：表达力天花板最高——知识、事务、资料一个模型全装下；后续任何新需求（比如加"设备登记"）都是建一个数据库块，不用改代码。

**缺点**：**工程量是 A/D 的三倍以上**；富文本编辑器、多视图切换、跨页引用每一项都是独立的坑；统计与提醒要自建通道。

**风险**：烂尾风险五案中最高——很容易花一个月还在打磨编辑器，忘了本来要管科研。

## 7. 工作量估计

页面树+Markdown 编辑器+基础数据库块（表格）：8~10 天；看板/日历视图+模板：+5 天；反链+仪表盘聚合：+5 天；打磨无边。

## 8. 何时选它

把系统当**知识库+事务管理二合一**、喜欢 Notion 的自由、且能接受 1~2 个月的开发周期——选 C。若是"先把科研管起来"，C 的性价比最低。
