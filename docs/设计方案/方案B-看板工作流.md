# 方案 B · 看板工作流（Focalboard 式）

| 一句话定位 | 一切皆卡片：课题是一块板，论文流水是一条板，用拖拽组织全部科研工作 |
|---|---|
| 交互重心 | 看板（列=状态，卡片=事项） |
| 数据范式 | 通用块模型（blocks 表 + JSON 字段） |
| MVP 工作量 | 约 6~8 个集中开发日 |
| 成长路径 | ★★ JSON 范式与关系型不兼容，后期转向需数据迁移 |

---

## 1. 核心理念

- 不为"课题/论文/实验"分别建模，**统一抽象为卡片**：一个实验步骤是卡片，一篇论文是卡片，一张卡片上可以有子卡片；
- 板（Board）是容器：催化课题一块板，论文投稿一条流水板，"2032 毕业"一块总览板；
- 列（Column）完全自定义：同一块板今天可以是"待办/进行中/受阻"，明天可以改成"材料制备/表征/分析"——**状态跟着工作流走，而不是工作流跟着软件走**；
- 卡片的字段（截止日、优先级、参数……）全部放进 JSON 字段，新需求 = 新字段，不用改表。

## 2. 借鉴的开源项目

| 项目 | 借鉴点 |
|---|---|
| [Focalboard](https://github.com/mattermost/focalboard) | **通用 blocks 模型**：boards、views、cards、子任务全部是 `block` 表中的一行（id / parent_id / type / fields JSON / position）；一份卡片数据渲染看板、表格、画廊、日历四种视图 |
| [Planka](https://github.com/plankanban/planka) | 看板交互细节：卡片侧滑详情、清单、截止日期徽标、拖拽排序的 position 策略 |
| [Wekan](https://github.com/wekan/wekan) | 卡片归档/导出思路（JSONL 归档格式，参考其 Focalboard 导入导出文档） |

### 3.2 页面清单（6 页）

板列表（=课题/论文/总览）/ 看板视图（板内四视图切换）/ 卡片详情（侧滑）/ 日历视图（全部板卡片按日期）/ DDL 板（按月分列的倒计时墙）/ 设置

### 3.3 关键交互

- **拖拽即状态**：卡片跨列拖动 = 状态变更，自动记时间（用于周报统计）；
- **同一份卡片四种视图**：看板/表格/日历/画廊，只是 query 不同（Focalboard 核心思想）；
- **卡片字段面板**：每个板可自选显示哪些徽标（截止日/优先级/参数摘要）；
- ⌘K 速录默认落在当前打开的板。

### 3.4 视觉风格

Trello/Planka 风：彩色列头、卡片阴影、封面色条；比方案 A 视觉更重、更"图形化"；支持按课题给板上色。

## 4. 数据库设计

### 4.1 表清单（5 张）

| 表 | 职责 |
|---|---|
| board | 板（课题板/论文流水板/总览板） |
| block | **万能块**：列、卡片、清单、评论、附件全是 block 行 |
| ddl | 独立 DDL（倒计时墙需要，建议保留关系型） |
| setting | 配置 |
| backup_log | 备份记录 |

### 4.2 核心表 DDL（SQLite）

```sql
CREATE TABLE board (
  id    INTEGER PRIMARY KEY,
  name  TEXT NOT NULL,
  icon  TEXT, type TEXT,             -- 课题/论文/总览
  color TEXT, position REAL
);

CREATE TABLE block (
  id         TEXT PRIMARY KEY,       -- UUID
  parent_id  TEXT,                   -- 板→列→卡片→清单 的树
  board_id   INTEGER REFERENCES board(id),
  type       TEXT NOT NULL,          -- column/card/checklist/comment/attachment
  title      TEXT,
  fields     TEXT NOT NULL DEFAULT '{}',  -- JSON：一切业务字段
  position   REAL,
  created_at TEXT DEFAULT (datetime('now')),
  updated_at TEXT
);
CREATE INDEX idx_block_parent ON block(parent_id);
CREATE INDEX idx_block_board  ON block(board_id, type);

-- "未来7天到期的卡片"：JSON 路径查询
-- SELECT * FROM block WHERE type='card'
--   AND json_extract(fields,'$.due') <= date('now','+7 day')
--   AND json_extract(fields,'$.done') IS NULL;

CREATE VIRTUAL TABLE block_fts USING fts5(title, fields, content='block');
```

### 4.3 设计取舍

- **加需求不改表**：论文流水线的"阶段"、实验的"参数"、成果的"作者排序"全部是 fields 里的 JSON 键——开发最快；
- **代价一：查询弱**。跨板统计（"本月完成多少任务"）要解析 JSON，聚合查询比关系型啰嗦且慢；
- **代价二：约束弱**。字段拼写错误（`due` 写成 `duedate`）数据库不报错，需要应用层守恒；
- **代价三：不可逆**。JSON 块模型一旦积累了数据，想转关系型（方案 A/E）只能写迁移脚本逐字段搬——这是本方案最大的长期风险。

## 5. 对需求报告的覆盖度

| 需求模块 | 覆盖情况 |
|---|---|
| 任务 / 论文流水线 / 看板视图 | ✅ 强项（天生契合） |
| 课题（容器） | ✅ 完整（=板） |
| DDL / 里程碑 | ✅ 保留关系型表 |
| 仪表盘 / 周报 | ⚠️ 简化（跨板聚合统计实现较绕） |
| 实验记录 | ⚠️ 可用但结构松（参数在 JSON 里，搜索尚可、筛选弱） |
| 成果对照 / 报销 / 文献 | ⚠️ 需后补（继续加 JSON 键，管理会渐乱） |

## 6. 优缺点与风险

**优点**：可视化程度最高；论文流水线、受阻任务这类"状态流转"场景表达力最强；字段扩展零成本。

**缺点**：统计报表是短板（而这恰是毕业对照需要的）；时间维度（倒计时/甘特）靠约定而非模型保证。

**风险**：JSON 范式锁定。个人工具的归宿往往是"统计与回溯"，块模型在这里最吃力。

## 7. 工作量估计

看板核心（板/列/卡片/拖拽/详情）：6~8 天；日历视图 + DDL 板：+2 天；周报聚合：+2~3 天（比 A 费劲，需扫 JSON）。

## 8. 何时选它

**视觉型思维**、日常打开软件第一眼想看到"板"、论文多且阶段流转频繁——选 B。但要接受"毕业对照/统计"永远是二等公民，且范式后期难回头。
