## 2. 两个决定性维度

五个方案的差异本质上是两个选择：

```
                    开发量 / 结构完备度
                    小 ◄──────────────► 大
                 ┌─────────────────────────────┐
   记录自由度高  │  D ■■■      C ■■■■■         │
                 │                             │
                 │  A ■■■■     E ■■■■■■        │
                 │  B ■■■                      │
   结构严谨度高  └─────────────────────────────┘
```

**范式之争比功能之争更重要**：A/D/E 同属关系型范式，表结构互相兼容，今天选 A 明天长成 E 是零迁移；B/C 把业务字段装进 JSON，一旦落地就很难回头——**如果不确定，别选 B/C 起步**。

## 3. 选型决策树

- 想**两周内先用起来**，以任务驱动每天 → **A**
- 日常**以实验记录为绝对主体**，信奉"先记下来再说" → **D**
- 视觉型思维，靠"板"组织工作，论文流转频繁 → **B**（接受统计弱 + 范式锁定）
- 想要 Notion 式自由、系统即知识库，且不怕 2 个月工期 → **C**
- 不赶时间、想一步到位建齐全部模块 → **E**

## 4. 我的推荐

**首选：A 为骨架 + 吸收 D 的实验条目表 + 按需引入 E 的模块（记作 A+D 混合）。**

理由：

1. **数据上无冲突**：A 的 8 张表 + D 的 `entry` 表是两套独立表，混合就是 9~10 张表的 SQLite，字段各管各的；
2. **两条主路径各取所长**：任务/DDL/倒计时走 A 的结构化路线（项目管理感），实验/文献/开销走 D 的流水路线（记录摩擦最低）——正好对应需求报告 2.1"容器—流水"两层模型；
3. **成长路径清晰**：这套混合体就是方案 E 的子集，毕业对照、论文流水线等 P1 模块将来按 E 的表结构逐个加上即可，永不返工；
4. **规避了两个头号风险**：B/C 的范式锁定，和 E 的"空系统劝退"（MVP 只有真正会用的功能）。

若不想混合、坚持纯一方案：**A 最稳**（结构化能力保底），**D 最贴习惯**（但接受弱项目感）。

## 5. 无论选哪个都不变的决定（共同技术底座）

| 项 | 决定 |
|---|---|
| 数据库 | SQLite 单文件 + FTS5 全文索引 + WAL 模式 |
| 架构 | FastAPI（Python）后端 + Vue 3 前端，本机 localhost；M4 可选 Tauri 打包 |
| 账号 | 单用户口令登录 |
| 数据安全 | 每日自动备份（保留 30 份）+ 一键全量导出 JSON/Markdown |
| 可扩展 | 业务表带 owner 字段与软删除，为课题组化（v0.1 存档版）留路 |
| 界面 | 中文，1366×768 起步，仅电脑端 |
